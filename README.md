# ЮК Синай · Новости — отчётный Telegram-бот

Отдельный Telegram-бот в стиле `prikaz-control`, но для подписок клиентов `sinai-news-bot2`. Интерфейс **UI-first**: обработчик Telegram только читает локальную кэш-БД и отвечает сразу; сетевые проверки amoCRM и полный пересчёт выполняются **в фоновом потоке**. После завершения готовые цифры подменяют сообщение «Сверяю…» в том же чате, без дополнительных команд.

## Что будет в отчёте

```text
📊 ЮК Синай · Новости
📅 Отчёт: 14.10.2026

👤 Павел — 50 всего (+3 за день)
👤 Ольга Шевелева — 45 всего (+3 за день)
👤 Юлия Миллер — 37 всего (+5 за день)
👤 Юлия Дегтярева — 62 всего (+2 за день)

👥 Итого: 194 · +13 за день
```

Цифры выше вымышленные. Отчёт «15.10» по расписанию в 09:00 показывает *всего на момент формирования*, а «за день» — новых подписчиков за **полные предыдущие сутки 14.10**. `/today` показывает неполный текущий день. Историческая команда `/report YYYY-MM-DD` считает добавления за выбранную дату, но показатель «всего» всё равно отражает подписчиков **на момент последней сверки**, а не состояние на историческую дату.

Под отчётом **только три кнопки дат**: `◀️ 13.10` · `14.10` · `15.10 ▶️`. Средняя кнопка показывает выбранную дату и ничего не делает. Если справа завтрашняя дата, она также неактивна. Обновление отчёта вручную доступно командой `/refresh YYYY-MM-DD` (или `/refresh` для вчера).

## Установка на VPS

Этот проект должен быть **отдельной папкой**, рядом с текущим `sinai-news-bot2`. Не останавливайте клиентского бота.

```bash
cd ~/sinai-news-report
python3 -m venv venv
venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
nano .env
chmod 600 .env
venv/bin/python main.py
```

В `.env` **обязательно**:

- `REPORT_TG_BOT_TOKEN` — токен **НОВОГО** Telegram-бота от BotFather. Не используйте токен клиентского бота, иначе возникнет конфликт getUpdates.
- `REPORT_CHAT_ID` — личный цифровой Telegram ID руководителя, которому разрешён доступ. Других людей можно добавить через `ALLOWED_USER_IDS=123,456`.
- `SOURCE_DATABASE_PATH` — путь к SQLite-базе основного бота. По умолчанию `../sinai-news-bot2/data/sinai.sqlite3` относительно этой директории.
- `AMOCRM_BASE_URL` — адрес amoCRM. `AMOCRM_ACCESS_TOKEN` не обязателен, когда основной бот сохраняет рабочий OAuth-токен в `settings.oauth` той же SQLite-базы.

В **новом** отчётном Telegram-боте отправьте `/start`. Это мгновенно откроет меню и **подпишет этот Telegram ID на автоотчёт**. Никто, не нажавший `/start`, автоотчётов не получит. Повторные `/start` не дублируют подписку.

`/report` или `/yesterday` — отчёт за вчера; `/report 2026-10-14` — за дату; `/today` — текущий день; `/refresh` — полная фоновая сверка за вчера; `/status` — состояние; `/start` — меню и регистрация. Если кэш свежий (по умолчанию 15 минут), ответ содержит готовые данные без запросов в CRM. Иначе показывается старый снимок с предупреждением или мгновенное «Формирую…», и начинается фоновый расчёт.

**Требуется Python 3.10+** с `zoneinfo` и системной базой временных зон. Поддерживается запуск именно `python main.py` (после активации `venv`: `source venv/bin/activate`). Дополнительной БД PostgreSQL и Redis не нужно.

### Автозапуск systemd

```bash
sudo tee /etc/systemd/system/sinai-news-report.service >/dev/null <<'UNIT'
[Unit]
Description=Sinai News Telegram Reporting
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
WorkingDirectory=/root/sinai-news-report
ExecStart=/root/sinai-news-report/venv/bin/python /root/sinai-news-report/main.py
Restart=always
RestartSec=5
Environment=PYTHONUNBUFFERED=1

[Install]
WantedBy=multi-user.target
UNIT
sudo systemctl daemon-reload
sudo systemctl enable --now sinai-news-report
sudo journalctl -u sinai-news-report -f
```

Замените `/root` на актуальную домашнюю директорию пользователя, если проект расположен не в `/root`.

## Надёжность и смысл чисел

- **Одна сделка = один клиент**, независимо от числа привязок Telegram и MAX. Считаются сделки из `users.lead_id` основного проекта, имеющие `subscribed_at`; люди без связанной сделки в отчёт по менеджерам не попадают (пока не будет синхронизации). Дата добавления — минимальная `subscribed_at` среди платформ для сделки.
- Приоритет: 1) поле `responsible_user_id`, если текущий ответственный уверенно соответствует одному из четырёх указанных людей; 2) иначе **`Бриф → Менеджер`**. ID поля автоматически ищется через метаданные групп и полей amoCRM. Если такое поле нельзя определить однозначно, укажите `MANAGER_FIELD_ID` в `.env`.
- Порядок имени и фамилии неважен, учитываются `ё/е`, регистр, `Юля/Юлия`, инициалы и небольшие опечатки фамилии (только вместе с подтверждённым именем). Если совпадение неоднозначно или менеджер не найден, сделка **полностью исключается из статистики**. Фамилия `Карепов` соответствует Павлу. При смене ответственного/поля CRM история отчёта при следующем полном пересчёте будет пересчитана по **актуальным** данным сделки.
- Сначала используются пакетные `GET /api/v4/leads` с `filter[id]` (80 ID за запрос), если API игнорирует или запрещает фильтр — безопасное переключение на одиночный `GET /api/v4/leads/{id}`. Пользовательский UI при этом не блокируется. Ограничение на amoCRM: менее 4 запросов/с суммарно, параллельность 4. Запросы не создают и не изменяют сделки.
- Если по причине HTTP 401/429/500 или сетевой ошибки завершить сверку нельзя, **новые цифры не сохраняются**: пользователю показывается ошибка и, при наличии, предыдущий кэш с явной маркировкой. Удалённые и недоступные сделки не учитываются.
- Автоотчёт планируется каждый день в **09:00 Asia/Krasnoyarsk**. Сначала приходит сообщение-состояние, которое **редактируется после завершения сверки**. Дата и получатель фиксируются в локальном `data/report_state.sqlite3` перед Telegram send, чтобы повторный старт процесса не создавал дублей. Если сеть оборвалась *после* принятия Telegram, но до получения ответа, статус помечается `unknown`, автоматическое повторение отключено (невозможно гарантировать ровно-одну доставку при неоднозначном сетевом результате).
- Основная SQLite открывается только с `mode=ro`. Все подписки на автоотчёты, кэш и состояния отправок лежат в **отдельной** базе `data/report_state.sqlite3`. Основной процесс можно не останавливать. Если главный бот обновляет токены OAuth, отчётный бот читает их из исходной SQLite; при 401 повторно извлекает актуальный токен.
- Только `REPORT_CHAT_ID` и `ALLOWED_USER_IDS` имеют доступ к интерфейсу в **личных чатах**; остальные запросы молча игнорируются. Бот не передаёт сведения о клиентах сторонним чатам.

## Проверки

```bash
venv/bin/python -m unittest discover -s tests -v
```

Юнит-тесты не подменяют проверку на живом аккаунте amoCRM. В частности, необходимо подтвердить, что реальное поле `Бриф → Менеджер` соответствует правильному `field_id`, а сервисный аккаунт имеет права читать перечисленные сделки.

## Обновление существующей установки

Замените только `main.py` в `/root/sinai-news-report`, затем перезапустите **только отчётного бота**. `.env`, `data/report_state.sqlite3` и база основного бота не изменяются. Кэш прежней версии будет автоматически пересчитан при следующем открытии даты.
